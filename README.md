# Three Kingdoms HD-2D（三国 HD-2D）

一款回合制三国战略游戏的 HD-2D 重制：像素角色立在 3D 地形上，加上实时光影、景深与后期。玩法规则和数值参照 1992 年 FC 游戏《三國志II 覇王の大陸》。游戏用浏览器运行（three.js），也能打包成 Electron 桌面版。

> 本项目是非官方、非商业的同人重制，与 Bandai Namco 无关。仓库不包含原版 ROM，但包含原版和 PS 复刻版音乐及部分音效。立绘等美术由 AI 生成，经人工筛选与修改。

## 项目结构

```
hd2d-mvp/
  index.html          游戏入口
  save-editor.html    存档（记录）编辑器
  vignettes.html      命令演出预览页
  src/
    core/             规则层，不依赖渲染：
                        game.js 战略层与全部命令、ai.js 战略 AI、warcore.js 开战与战后写回、
                        field.js 战争地图、tactical.js 白兵、skirmish.js 白兵与单挑结算、
                        saveedit.js 记录编辑、ahuinan.js 阿会喃漏洞模式
    war/              战争地图 3D 视图（board、units、overlay、camera、pick、interact、play、probe）
    *.js              three.js 场景（strategy*.js 战略地图、warview.js 战场、tacticalview.js 白兵、
                      duelview.js 单挑等）与流程、界面（app.js、ui.js、ui.css）
  data/
    game-data.json    武将、城市、地图、事件等全部规则数据
    thanks.txt        片尾鸣谢名单
  assets/             美术、3D 模型与音效（素材包，见下文）；manifest.json 列出可选资源
  tests/              测试（*.test.mjs），公共辅助函数在 game.mjs
  tools/              开发服务器、无头浏览器、截图与检查、模拟，以及美术切图与烘焙脚本
  desktop/            Electron 打包脚本
```

## 获取代码与素材

大型美术、3D 模型、音乐、音效及桌面图标集中在 [GitHub Releases 素材包](https://github.com/jicki/threekindoms/releases/tag/assets-3)，安装后沿用 `hd2d-mvp/assets/` 及桌面图标原目录。地方装备小图与新增头像随代码分发，见 `hd2d-mvp/assets/regional/`。近期重绘的立绘和动作也随代码分发，见 `hd2d-mvp/assets/portrait-refresh/`。

```bash
git clone https://github.com/jicki/threekindoms.git
cd threekindoms
make assets  # 本地开发、测试或桌面版打包前运行
```

`ASSETS.lock.json` 固定下载地址、大小和整包 SHA-256。`ASSETS.sha256` 固定每个素材文件的路径和 SHA-256。`make assets` 会先校验现有文件，缺少或不匹配时下载并校验整包。通过逐文件校验后安装清单里的素材。已提前下载 ZIP 时，可用 `python3 hd2d-mvp/tools/assets_pack.py install --archive /path/to/threekindoms-assets-3.zip` 离线安装。

更新素材时先更新 `ASSETS.sha256`，再用 `python3 hd2d-mvp/tools/assets_pack.py pack /path/to/threekindoms-assets-4.zip` 打包。将 ZIP 发布到新的素材 Release，用打包工具输出的大小和 SHA-256 更新锁文件。旧的 Release 供旧版代码继续构建。

## 运行

需要 Node.js 22 以上和 Python 3。

```bash
npm --prefix hd2d-mvp/desktop install     # 首次：安装 three.js、字体和 Electron
python3 hd2d-mvp/tools/serve.py 8677      # 启动开发服务器
```

然后用浏览器打开 http://127.0.0.1:8677/ 。进入及刷新时沿用「☰ 系统 → 声音」的偏好。在网址后面加 `?mute` 可临时静音。

### 战场操作

在「军 → 出阵」选定目标后，可在选将时查看进场方向、城门方位、外围地形和攻方布阵区。天气和援军按当前战役规则显示。侦察目标及相邻城市后才能看到对应守军或可能出援的武将数。

在「人物志」选中武将，点击「动作预览」可播放行军、白兵和单挑，并切换朝向。白兵和单挑按当前武器采用实战动作，行军展示战场使用的行军素材。预览同时列出当前兵种与生效的被动。

可点击武将所在格或姓名选择武将；画面拥挤或人物被遮挡时，使用战场右下角的「选将」从我军名单选择。布阵时也可以用此名单或手机上的 ‹、› 切换武将；电脑键盘使用 `[`、`]` 切换。正在选择攻击或计略时，先完成或取消该指令再使用名单切换。点击姓名会优先选中对应武将，若姓名挡住目的地，可按住 `T` 或点「地形」后选择地格。

君主列传新版战场开场聚焦可控总大将。桌面可用滚轮或 `+`、`-` 调整远近，手机可双指缩放，两端都有「＋ / −」及「全图」按钮。`C` 聚焦当前武将或总大将。3D 可按 `Tab` 切换俯视图。人物卡上的内外城门说明独立换行，完整显示封闭、突破和机动力消耗。

### 多层攻城

君主列传的攻城战以中央据点为目标。洛阳、长安等设有外城和内院，普通城镇采用单层城防，关隘沿固定道路轴设内外关门。攻方进入封闭城门额外消耗 2 点机动力并突破，此后双方可通行。突破不可撤销，攻方占领中央城格或击败敌方总大将即可取胜。布阵、移动预览、小地图和手机操作使用同一套地形规则。

攻方在城外施计时受未突破的内外城门和城墙阻隔。突破后可沿对应的门口施计，墙格仍阻隔计策和范围效果，连线仅擦过墙角时可通行。白兵按交战地形结算，中央城格使用守城阵型。

君主列传启用新版攻城规则的扩大战场中，守军可在封闭的内外城门迎击。火计、乱水可从门格或门后第一格打到正前方两格内的单个敌军，仍按目标地形判断。落石、连弩须站在门格，且敌军紧邻门外。迎击判定阈值减 10、最高 75，计策仍消耗机动力并遵循习得条件。范围计策和专属计策继续受城墙与城门阻隔。旧布局、未启用新版规则的记录及原版保留原有判定。

修订 9 为 39 处据点配置了不同的城廓、门轴和外围。洛阳有 13×9 格横向外城与朱瓦三层宫阙，长安有 11×11 格外城与青瓦重檐宫院，新野为 9×7 格旱壕城。水城的水岸位置随城市固定，山城和关隘以岩坡收束来路。攻军在实际来路的门桥外布阵，守军分驻外院和内院。关门偏移时可沿门道侧移。全战场为 32×19 格。 [各据点城防一览](docs/changelog/v0.3.11.md#据点配置)

修订 12 将君主列传的 39 处战场扩为 **40×27**。攻军从城外集结，主路通正门，侧路可绕向另一座门。渡桥接续越河的路线。占住前哨且仍有士兵的武将次日起为己方提供 2 点机动力。道路每格少耗 1 点机动力，最低 1 点。2D、3D、布阵预览和电脑共用道路与前哨数据。旧记录和已经中断的战斗按原有尺寸恢复。详见[战场更新日志](docs/changelog/2026-11-21-battle-approaches.md)。

君主列传新开局采用修订 17。**39 处战场和 146 条相邻来路**的尺寸为 **44×30 至 52×34 格**。陆路攻城时，全军按来路在同一个角区集结，布阵期间可整队改选任一角区。关隘沿各自谷道集结，建安与夷洲之间可整队改选登陆点。32 座城市加宽街区，商店分散到不同角区。宛城战先夺开阔地上的外营，再打城门。并州西岸仍沿木桥通往西门。旧战役在战略回合可主动升级，中断战斗按记录里的布局和位置续玩。 [整队集结与镜头操作](docs/changelog/2026-11-21-army-deployment-and-zoom.md) · [39 处地形一览](docs/changelog/2026-11-21-regional-battlefields.md#各据点设计)

点击「全图」查看战场，再按 Esc 或点地图即可回到查看前的视角。桌面触摸板支持小幅连续缩放和捏合，普通滚轮、键盘「＋ / −」及缩放按钮也可调整远近。

地域战场的三维和平面版采用自然土路、错缝石板和疏密变化的树林。水岸根据深浅配色，沿江偏灰绿，夷洲由青绿浅滩过渡到深蓝外海。城防使用斜收石墙、拱形门道和翘檐门楼，洛阳与长安的主门按既有墙格加宽。新增地表材质合计约 128 KiB，随代码提供。贴图读取失败时可用既有材质继续对战。 [战场材质更新](docs/changelog/2026-11-21-battlefield-materials.md)

战略沙盘为襄阳使用较复杂的大城模型，江州、宛城、夷洲使用县城模型，关隘使用关楼模型。某类模型加载失败时会在对应据点绘制有城墙和屋顶的程序模型。

标题阶段以每秒最多 30 帧更新背景。行军素材在进入战场时加载，普通与特色兵队在进入白兵时加载。切换到平面地图时释放全尺寸的 3D 后处理缓冲，返回 3D 时按当前画质重新配置。

电脑攻方沿实际门桥寻路，遇守军挡路可发起白兵。孤立的攻方总大将可先避战，兵力占优时后援可跟进；主将受威胁时优先保卫。电脑守军从城内迎击，必要时绕内墙到受威胁的城门，拦截已入城的敌军，主将坚守中央。粮草临近耗尽时仍可派人买米。电脑之间的抽象结算也读取同一城防地形判断水域。战斗中断保存布局修订、部队位置、城门状态及攻方主将当日避险状态。

扩大战场的默认镜头将双方部队与城墙、护城河同时纳入取景。手机使用适应屏幕的平面取景，仍可手动拖动、缩放和复位，桌面保留原有俯瞰与旋转。进入战场后预取当地白兵地形，同季节共用素材。白兵在冲锋演出期间按实际兵队读取动作图，单挑特写从开始交战时预取。手机白兵地表纹理由每格 56 像素降为 40 像素，场地格数和坐标保持一致。选中计策后预取该计策的短片，确认时等图最多 1.2 秒，超时后用文字和战场效果结算。

手机点按靠近工具栏的可见地格仍可预览路线，确认后才会移动。桌面平面战场底部为换行的城门说明留出空间。单挑命中提示按武将当前的被动、体力和骂倒状态计算，受骂倒时可查看同一招式调整前后的概率。

较早的城防验证曾用九个新增据点的 19 条入口、每条八组相同种子，对修复阻隔后的两种电脑决策进行配对模拟。各将设定为 700 兵、武 70、智 60、三级，双方粮草均为 9999；两组攻方使用不同电脑角色配置，守方均为 3 将。3 将攻 3 将时，攻方胜场分别为 4→5 和 0→0（各 152 场）；6 将攻 3 将时分别为 36→61 和 12→28（各 152 场），所有战斗均发生白兵接触。修订 8 与修订 9 的配对结果见 [城防更新日志](docs/changelog/v0.3.11.md#平衡验证)。

### 战场生死

开局时或游戏中的「☰ 系统 → 战场生死」可选择原版规则或「不战死」，选择随本局存档保存。开启后，白兵、单挑和计略中体力归零的武将与君主会退出战场并被对方俘获；电脑之间的战争也将伤亡改为被俘。君主恢复体力至 30，但不超过其体力上限。

战败君主无路可退时优先由胜方俘获；俘获方没有可用位置时君主下野。君主被俘或下野后，原势力有部下时选择继承者，否则势力灭亡；总大将被俘仍会结束战斗。开启不战死不会阻止病逝，病逝由「武将不老」单独控制。单挑宝物仍须实际斩杀才能获得，被俘不会触发斩杀奖励。

### 背景音乐

游戏会自动检查本地可选音频。自带服务器会批量报告清单中可用的素材，减少启动时的逐项探测；静态托管或旧服务器自动回退到逐项检查。在标题页或游戏中的「☰ 系统 → 曲目」可以切换已提供的音乐版本，选择保存在当前浏览器中；浏览器可能要求先点击页面才能播放。没有可用音频时，部分场景使用合成音乐。已有的 `remix/` 素材仍显示为 Remix，不会误认为 PS 复刻版。

原版和 PS 复刻版音频放在 `hd2d-mvp/assets/audio/original/` 和 `hd2d-mvp/assets/audio/ps/`，文件名与 `assets/manifest.json` 中的对应场景一致。已收录的 16 首背景音乐、事件短曲、单挑音效，以及爆炎和碰撞音效由锁定的 Release 素材包提供。其他本地音频文件仍被忽略。音频保留现有的 M4A 和 MP3 格式，避免对有损素材重复转码。构建 Docker 镜像或桌面版时会打包这些音频；加入或更换音频后需要重新构建。

### 使用 Docker Compose

需要 Docker 和 Docker Compose。全新克隆后可直接运行 `make build` 或 `make up`。构建优先使用项目根目录中与 `ASSETS.lock.json` 下载地址同名的 ZIP，例如 `threekindoms-assets-3.zip`。素材包大小及 SHA-256 一致时直接解压。没有匹配的项目 ZIP 时，构建会检查 BuildKit 缓存，必要时才从锁定的 Release 下载。每个解压后的文件仍会逐一校验。ZIP 和构建缓存只在构建阶段使用，运行镜像只包含解压后的素材，编辑器上传目录继续使用独立数据卷。

Dockerfile 从 `reg.deeproute.ai` 拉取 Node 和 Python 基础镜像。本次验证的镜像为 `linux/amd64`；在 ARM 主机上运行需要支持 amd64 模拟。

Docker 构建使用 `docker/package.json` 和 `docker/package-lock.json`，仅安装 Three.js、马善政和思源宋体。桌面版使用 `hd2d-mvp/desktop/` 的依赖清单和锁文件。更新这三项共享依赖时，同步更新两处锁定版本。

首次部署，或更新游戏代码、规则数据、依赖、构建文件或素材锁定文件后，运行 `make up` 即可构建并启动。只需要生成镜像时执行 `make build`。只改端口、令牌等运行配置时，可用 `docker compose up -d --no-build` 复用已有镜像；只改文档或测试时也可继续使用已有镜像。

执行 `cat ASSETS.lock.json` 查看当前工作区构建所用的素材版本。下载地址中的 Release 标签即素材版本，`sha256` 和 `size` 是精确的校验值。也可以执行 `git show HEAD:ASSETS.lock.json` 查看已提交的锁文件，将 `HEAD` 换成目标提交号即可查询历史版本。只更新游戏代码且素材安装器、锁文件和素材清单未改变时，Docker 可以复用素材层。

本地 ZIP 损坏、版本不匹配或被移走时，构建会尝试已校验的缓存或重新下载。首次下载成功的 ZIP 和 `npm ci` 下载的依赖分别保存在当前 BuildKit 构建器的缓存中。基础镜像、本版本的 npm 依赖与素材 ZIP 均已缓存时，构建步骤可以断网运行。清理缓存、使用 `--no-cache` 或更换构建器后，仍可放回项目 ZIP 直接校验解压，缺失的依赖需要联网下载。下载中断或远程包校验失败会中止构建并保留已有镜像，恢复网络后可用 `make build` 或 `make up` 重试。`make assets` 也可直接使用项目根目录中的 ZIP。

```bash
make build    # 校验素材并构建镜像
make up       # 构建镜像并在后台启动
make ps       # 查看服务状态
make logs     # 查看服务日志，按 Ctrl+C 退出
make down     # 停止并移除容器
```

客户端提前断开连接时，日志会保留一条简短提示；其他服务端异常仍会输出完整堆栈。

打开 http://127.0.0.1:8677/hd2d-mvp/ 。默认只监听本机的 8677 端口；可以通过环境变量修改监听地址和宿主机端口，例如：

```bash
GAME_BIND_ADDRESS=0.0.0.0 GAME_PORT=8080 make up
```

游戏记录保存在浏览器本地，容器不保存存档；更换浏览器或访问地址后不会自动共享记录。
普通记录读取时会检查武将、所属势力及城市武将引用。遇到损坏记录时，会尝试读取上一份有效备份。普通档和快捷档成功覆盖后，上一份有效主档成为备份。如果主档写入失败，旧主档保持原样，已轮换的备份会恢复到写入前的内容。
普通记录和快捷存档使用 IndexedDB 协调不同页面的写入，支持 Web Locks 时也会使用该锁。IndexedDB 不可用时会提示无法安全写入。当前客户端保护较新版本留下的普通档、快捷档、自动续玩与战斗中断。记录编辑器遇到较新版本的导入文件时，会提示更新客户端。已打开的旧版页面可能沿用旧的写入机制，更新后请刷新或关闭这些页面。

读取君主列传的旧记录后，可在己方战略回合选择「☰ 系统 → 记录 → 升级当前战役」，启用当前修订的规则、寻访人物和地方武器。升级保留年月、命令书、武将属性与兵力、装备、城池资源、外交关系及已设定的开关。早期记录同时补齐张昭、张纮和张绣的寻访队列，保留已有分身及归属。开局补给只在新开局发放。

确认升级后可以立刻继续游玩。用「记录进度」另存一格可保留原记录，也可使用快捷存档保存升级结果。中断战斗按保存时的规则恢复，战场准备完成后才清除中断档。初始化失败时会返回标题，玩家可以重试。结算后可在战略地图升级。原版、服务器自定义版本及已下架独立剧本的记录沿用各自的版本归属。下文提到沿用旧规则的存档，指未经战役升级的记录。战役规则修订号与存档结构版本分别保存，后续规则迁移可按战役修订追加。

### 游戏版本管理

管理员可在标题画面选择「☰ 系统 → 版本管理」，或打开 `/hd2d-mvp/admin.html`。管理页面可以基于原版、内置版本或已发布版本编辑人物属性、出生与登场信息、人物关系、新武器、新防具和新技能，再发布给使用同一服务器的玩家。原有美术素材包提供 237 套人物立绘及表情和 24 个武器图标。
手机窄屏下「版本管理与发布」默认折叠，展开后可载入、导入、导出及发布版本；编辑分类导航保持在页面顶部，操作状态在折叠时仍可查看。

标题提供「原版」和「群英新篇·君主列传」，以及管理员已发布的版本；新会话默认进入君主列传。君主列传包含此前「群英新篇」和「巾帼群英」的内容，例如可通过城市搜索登场的孙尚香、甄宓、貂蝉、蔡琰、王异、陈宫和高顺。编辑器可将这些人物以及陈到、辛宪英作为模板加入其他版本，并分别选择或上传立绘、平静／喜悦／愤怒／悲伤表情及动作。立绘和表情上传支持 PNG、JPEG、WebP；动作上传使用透明 PNG 或 WebP 正方形 4×4 网格，浏览器会规范为 512 × 512 PNG。帧的顺序与素材示例见 [角色素材说明](hd2d-mvp/assets/characters/README.md)。原有「上传人物图片」仍按旧版方式将不超过 64 KB 的图片放入版本文件，未单独配置表情时共用。

城市命令分为「城、军、仓、町、谋」。记录在「城」中，调遣在「军」中，赈济在「仓」中，医馆、书馆和铁铺在「町」中。同盟、诱纳和离间在「谋」中直接选择。调遣时在地图选可接收武将的邻城，选将页列出目标余位与本次上限。医馆、书馆和赏赐可选择一并执行。搜索、赈济、离间和诱纳可选择连续次数，逐次消耗命令书和资源，遇到人才、成功诱纳、资源不足或适用的停止条件时提前结束。征兵显示扣除预备兵后的缺额与本次上限。

战场计略确认面板可选择连续施放次数，逐次扣除机动力、计算随机数和经验，合并演出并逐次显示结果；目标离场、兵力耗尽、限制效果已生效、专属技能次数耗尽或战斗结束等情况会提前停止。单挑「说得」成功的普通武将保留白兵剩余兵力并在原地转投，忠诚按新势力和人物关系计算；被说服的总大将使原方战败。主动降参仍按俘虏结算。山贼、海贼袭扰的临时敌军不参与转投，仍按袭扰规则处理。电脑战场行动会跳过已转投武将，并在护卫堵住主将时尝试让行。白兵爆炎以将领最近一次移动方向确定落点，出界时不能使用，指向按钮时可预览范围。

君主列传的 39 处据点各有场景主题。统一条件包含 34 城，另外 5 处关隘可驻军。原有 30 城沿用各自的基础地形，新增据点使用各自固定地形。襄阳、江州的天然河道绕开城防并保持四向连通。3D 战场和手机平面战场共用各城防的门位、桥位及屋顶配色，手机平面底图预绘墙体和桥面，小地图同步显示城门状态。

#### 新战役玩法

君主列传新开局使用战役规则修订 12，固定名册共 284 人。陈群、钟繇、宗预等 11 人按年份在对应城市开放寻访，各自配有立绘、兵种和被动。旧档继续按保存时的规则游玩，中断战斗按记录恢复部队与城门。结束当前战斗后，可在己方战略回合手动升级。采用修订 2 至 8 的新版战场自定义剧本也可手动升级到修订 9。 [修订 11 人物一览](docs/changelog/2026-11-20-officer-roster-11.md)、[修订 10 人物与地方铁铺](docs/changelog/2026-11-20-regional-content.md)

修订 7 的城签以势力颜色显示城名，仅无主据点另显示归属。敌城的兵力与武将列表要先侦察，情报可保留三个月，易主即失效。电脑好战默认关闭，开启后的档位跟随开局难度。手柄可用「☰ 系统 → 手柄记录快捷键」设置普通和快捷存读档。

- 大地图运输可走最多三段连通的本势力道路，城市和关隘均可中转。选择目的地时可预览路线。出阵时会显示进场方向、天气、留守兵力和携粮天数。
- 城市的「太守委任」可安排防灾、征兵或买米，并设置保留金。每月己方回合起始最多执行两条，每条成功命令消耗一张命令书，至少留一张给玩家。关隘由城市直接补给。
- 一份新同盟持续 14 个月。遭攻击时，最多一个相邻盟城可派出两名有兵且可作战的非君主武将，出援城须留下太守，守方合计至多 10 将。每位援将要求出援城具备 60 米，补入守方共用军粮至多 60 米。与攻守双方均有同盟的势力保持中立。玩家可接受或拒绝求援，拒援或原计划因兵粮变化无法执行时，电脑寻找可用的盟城。玩家指挥实际归本势力的参战者，其他盟军自动行动，全体守军共用机动力。实际白兵、单挑和计策产生的俘虏按擒获者的势力结算，「说得」倒戈者即时跟随招降方。援军和其俘虏优先返回出援城，满员时安排到其他本势力据点，无处安置则下野。电脑之间的抽象战斗按双方主阵营安置俘虏。
- 电脑会考虑目标可能得到的援军、开战后暴露的侧翼和势力扩张速度。白兵尝试按射程、阵型和克制选目标，受阻时寻找短绕路。三个难度的电脑交战战力、计策和普通单挑命中阈值分别增加 2／4／6，白兵战术点增加 1／2／3。
- 出阵时根据月份与地区确定本场天气。雨天林地与非水军通过河格时多耗 1 点机动力，火系伤害降低 15%，「乱水」与「水攻」伤害提高 15%。普通弓兵的最大射程减一格。雪天林、平、山地多耗 1 点机动力，骑兵每白兵回合行动一次。
- 白兵进入河道时可走便桥，山地有狭道，城中有街巷和挡点。野战布阵优先令枪盾居前、弓兵靠后，同类相邻可相互支援。枪兵近身克制骑兵，骑兵近身克制弓兵，盾兵抗箭，锤兵克盾；加成与现有特色兵队属性共同结算。
- 「夹攻」要求智力 65，三格内目标旁要有另一名可接敌的友将，消耗 7 点机动力，打掉 115 兵。「破阵」要求智力 82，消耗 9 点机动力，打掉 50 兵并使目标下次白兵战力降低 10%，有效至下日结束。两者每场各可尝试两次，均受城墙和城门阻隔。
- 每名人物拥有一项被动，人物资料显示生效效果。关羽的「武圣」强化单挑首记普通攻击，黄忠的「定军强弓」强化白兵弓兵远射，郭嘉的「奉孝料势」强化虚兵、要击和破阵。普通文武按初始属性分配行军、攻防、计策或内政模板。全体 265 名武将及具体数值见 [人物被动清单](hd2d-mvp/docs/武将被动.md)。

新版关系补充刘备、关羽、张飞的结义，刘备与诸葛亮的君臣，曹操与夏侯惇的亲属，孙策与周瑜的朋友关系；这些关系只在启用新版玩法的记录生效。编辑器列出既有及新版关系，新规则拒绝同一种关系的反向重复；未启用新版玩法的旧版本仍按原有格式读取。

新版电脑选择进攻目标时兼顾守将、兵力、军粮与关隘；战场直行受阻时会在可达范围内绕行，持续跟随可行路线以避免重复往返，并优先攻击相邻且已明显虚弱的敌方总大将。关隘守方获得少量战斗优势，自动战斗也少量计入装备与关隘守备。电脑同盟报价超过 255 时按全额报价与支付；原版及缺少新版玩法标记的旧记录保留原有规则。

190 年起，新版玩法中的地方建言每个符合条件的势力每月有 3% 的检查概率，全图当月最多一次、同一势力至少间隔 24 个月；当月受灾、发生战争或遭袭的势力不会触发。玩家可选择花费 80 金使防灾＋5、土地＋3，或换取 100 米，也可暂不办理；电脑会根据粮食情况选择。资源和建设值遵守原有上限，选项显示上限内的实际增量；没有收益的选项不可选，重复选择不会重复扣费或领取。

君主列传修正电脑补兵：先使用后备兵，再按每 20 金征集 100 人；资源不足时仅补充可负担的人数，出阵整备也不再多征收不需要的兵。原版、十方诸侯及旧的已发布版本继续保留原版字节判断和扣费行为；管理员可在「君主候选」中为草稿启用修正规则，并发布新版本。此设置不改变玩家征兵规则。

君主列传的新开局中，公孙瓒、袁术、刘表的开局城市分别获得金与米各 900、450、1200，后备兵保留各城原值。这些数值改善单城势力的早期资源，玩家与电脑使用相同开局；编辑器的「君主候选」可调整各新势力的开局金、米和后备兵。已有存档的城市资源不会重置，君主列传的旧存档恢复后采用更新后的电脑补兵规则。包含开局资源、补兵规则或技能演出设置的已发布版本需要更新后的客户端和服务器。

君主列传的新开局启用增强灾害：洪水和旱灾仍在原有月份发生，标准地图的城市范围不变，扩展地图额外城市的灾害范围见上文。受灾时城市金、米各至少损失 50，土地和产业各至少损失 5，现有数量不足时最多扣除现有数量。防灾值越高，额外损失越少；洪水对米和产业、旱灾对土地和驻军的影响更大。同一城市在相邻月份连续受灾时，第二次的额外损失减半，但每次的资源和建设损失保底仍然生效。事件会显示实际损失。版本编辑器的「增强灾害影响」可为新开局启用或关闭此规则，开局时的设置随存档保存；已启用增强灾害的存档使用更新后的损失规则，未启用的旧存档和原版继续按原灾害规则结算。旧存档首次读取前未保存的受灾时间无法追溯。包含此设置的已发布版本需要更新后的客户端和服务器。

君主列传的新开局还启用山贼、海贼守城和电脑补兵优先级优化，可在版本编辑器的「君主候选」中分别设置；已有存档保留开局时的设置。190 年起，守军至少 100 人、太守体力至少 20 且粮草足够约 20 日的城市可能遭袭；每个符合条件的玩家势力每月抽取一次，概率为 5%，电脑为 1%。内陆城市当月发生暴乱时，同一次抽签可能引来山贼，玩家遇到的敌兵约为驻军的 30%；电脑遇到的暴乱袭扰更弱。其他暴乱冷却初期不叠加随机袭扰，近海暴乱不会引来山贼。全图每月最多一场，同一势力和城市至少间隔 18 个月；势力的城市受灾当月、经历普通战争的当月及下月不会遭遇袭扰，袭扰当月电脑不会再攻打该势力。辽东、青州、徐州、扬州、建安、交州和夷洲为近海海贼，其余城市为山贼。玩家遇到普通袭扰时敌兵约为驻军的 40%，最多 2000 人；电脑遭遇较弱并自动结算，贼军不会占领电脑城市。守城败北时城市金、米、土地和产业损失 5%；受到致命伤或被擒的普通守将战后下野，玩家君主阵亡则游戏失败，启用「武将不战死」时君主仍受保护。若玩家城市无人留守，城市变为无主。守城支持战场中断和手机自动续玩，临时敌军不会加入人物名册。

启用「优化电脑补兵优先级」并同时启用「修正电脑补兵」后，电脑优先考虑实际可补兵数，同时更重视前线和君主城的防守。已启用此优化的存档使用更新后的排序；原版及未启用优化的旧记录继续使用原有选择顺序。开启增强灾害、守城或新补兵设置的已发布版本需要更新后的客户端和服务器。

扩展剧本的白兵和单挑按当前装备选择剑、刀、长兵、弓或扇的动作。角色有合适的个人动作时优先使用，换装后缺少对应动作时使用该兵器的通用骑乘动作，人物资料仍显示本人的立绘和姓名。持弓将领会搭箭、拉弦并在松弦时发射，扇的近身挥击会带出独立的风弧。单挑的箭矢属于演出，双方仍须按原有条件进入单挑。命中率、伤害、射程和计略继续按各版本的规则结算。原版遵循既有动作选用规则，扩展剧本从旧存档读取已保存的装备。郭嘉的行军和白兵沿用 v0.3.9 的骑马格图，单挑单独加载重制动作。素材暂时无法读取时回退到原个人单挑动作。

君主列传的落日弓重量为 6，凤羽宝衣重量为 5。电脑会比较购买条件、价格和装备攻防。已发布的自定义版本使用各自的装备数值与技能配置，编辑器导入角色模板时可沿用已有的同名装备。

包含新武器类别、防具或搜索优先设置的版本需要更新后的客户端与服务器；已发布的旧版本仍可读取。升级后如果玩家仍开着旧页面，请刷新后再选择新版本。

上传独立素材前先在管理页面输入管理员令牌。输入图片最多 8 MiB、1600 万像素，单个素材压缩后最多 1 MiB，单个版本最多引用 128 个不同素材、合计 16 MiB；版本 JSON 本身仍限 1 MiB。动作图须包含透明背景和可见图像。素材按内容哈希去重，存放在版本目录的 `assets/` 中，由玩家按需读取；上传后放弃草稿或发布失败时，未引用素材不会自动删除。游戏会在加载动作网格时统一各帧的角色比例、适度减少脚底留白，并为白兵和单挑移动使用行军帧；过宽的单行动作条会重新排列为多行，避免在纹理宽度有限的设备上缩小整张动作图。

原版数据没有内置人物关系记录；编辑器列出当前版本的关系，支持筛选及添加亲属、朋友、父子、兄弟、结义、君臣等关系，也可输入不超过 16 字的关系名称。关系在双方资料中使用相同名称。君主列传的新开局启用关系效果：亲友和敌对关系可影响寻访、内政诱纳与战场笼络，按招募方和原势力君主与目标的关系综合判断，多条关系不叠加。一般诱纳的实际成功率最多变化 5 个百分点，特定人才寻访按原版的 16 档概率变化一档；原有无法招募条件不变。入仕时与新君主的关系可使忠诚增加或减少 5，非指定继位时可使忠诚变化增加或减少 2；已有 90 以上的入仕忠诚不会因此降低。亲近与敌对关系同时存在时抵消，无法识别的自定义关系只展示。玩家和电脑使用同样的关系规则。

启用旧版电脑战斗技能的战役，自动战争会将可施展的专属计略和单挑技折算为战力，双方各至多增加基础战力的 10%，且最多 12 点。修订 2 起对参战者的白兵攻防、计策命中、单挑和战术回复类被动估算战力，双方各至多增加基础战力的 5%，且最多 4 点。自动战争采用抽象结算。版本编辑器的旧技能模板可组合固定的损兵、伤体力、限制移动和损粮效果，供选择旧战场规则的版本使用。

君主列传的新开局还修正电脑诱纳概率：负值限制为零，避免原版的无符号数回绕导致必然成功。版本编辑器「君主候选」可配置该规则；设置随新开局保存，原版、未启用的已发布版本和旧存档保持原有计算。

十四类兵队均有独立绘制的 16 帧待机、行走、攻击和受伤等动作；素材不可用时回退原兵队画面。电脑间自动战斗仍是抽象结算：每名能带出特色队且体力未耗尽的武将至多增加 1 点战力，双方各以基础战力的 1/30 为上限，战报显示实际加成；不会额外抽取随机数。

例如，轻骑画面参考公孙瓒的白马骑军形象，可对照[《三国志》卷八](https://zh.wikisource.org/zh-hans/%E4%B8%89%E5%9C%8B%E5%BF%97/%E5%8D%B708)与[《三国演义》嘉靖本第十三回](https://zh.wikisource.org/zh-hans/%E5%98%89%E9%9D%96%E6%9C%AC%E4%B8%89%E5%9C%8B%E5%BF%97%E9%80%9A%E4%BF%97%E6%BC%94%E7%BE%A9/%E7%AC%AC013%E5%9B%9E)；兵队区分与武将能力相结合的玩法亦参考[《三国志14》出阵说明](https://www.koeitecmoamerica.com/manual/rtk14/en/5100.html)。这些兵队的属性和分配是本游戏的设计，不是对史料或其他游戏数据的直接复刻。

出生年份和出生地用于人物资料，登场年份、地点和方式决定人物何时进入游戏。原有君主的开局位置不可修改；如果调整登场导致某城开局没有武将，该城会成为无主城。编辑器还可将某个势力的开局武将设为额外君主候选；玩家开局时可以选择这些候选，其所在势力由选中人物统领，原君主留在该势力。此功能不增加势力数量，旧版本与原版保留原有七位君主。

服务器默认允许读取已发布版本，**未配置管理员令牌时不允许发布**。令牌需为 32–256 位不含空格的可打印 ASCII 字符，请使用密码管理器生成的高强度随机值。首次启动或轮换令牌时，在当前终端输入令牌（输入不会回显）：

```bash
read -r -s GAME_ADMIN_TOKEN
export GAME_ADMIN_TOKEN
make up
```

Compose 会将令牌的 SHA-256 校验值保存在独立的 `game_admin_token` 持久卷中，文件仅允许所有者访问；不会把令牌原文写入该卷、浏览器或版本文件。随后容器重启或重建时，即使没有环境变量，也会继续使用已保存的令牌。该配置依赖同一 Compose 项目中的持久卷；迁移宿主机或更换项目时需迁移该卷或重新配置令牌。已有部署升级到此功能后，首次启动仍需提供原令牌一次，才能写入新的持久卷。

发布时在管理页面输入相同令牌；发布成功后输入框会清空。需要轮换令牌时，以新令牌重新执行上述命令；启动后旧令牌失效。使用同一可信持久令牌文件的运行中实例会在每次发布认证时读取最新校验值，轮换后的认证请求会使用新令牌；只使用进程内令牌的实例不会自动同步。启动时非空的 `GAME_ADMIN_TOKEN` 总是覆盖已保存的校验值，因此轮换后应协调所有实例的配置，避免其他实例重启时再次提供旧令牌。令牌文件和所在目录须由服务运行用户或 root 所有；文件不得允许其他用户访问，目录不得允许其他用户或用户组写入。无效的环境变量、不可写或损坏的令牌文件会禁用发布并记录错误，不会用错误令牌覆盖已保存的配置。首次启动时传入的环境变量仍可被具有 Docker 管理权限的人查看；若不再需要它，可在终端执行 `unset GAME_ADMIN_TOKEN`，然后重新执行 `make up`。

静态服务拒绝访问隐藏文件及指向 `.env` 配置的链接，`.env*` 也被排除在 Git 和 Docker 构建上下文之外。仍建议不要把真实令牌放在项目目录内。默认端口仅绑定本机；通过网络管理时，应使用 HTTPS 反向代理保护令牌。

玩家在标题画面选择「☰ 系统 → 游戏版本」，新会话默认使用君主列传；即使版本服务不可用，也可选择原版和内置版本。每次修改后发布都会创建不可覆盖的新版本编号，原版及各版本的普通、快捷、自动和中断战斗记录分别保存。管理页面可以导入、导出版本 JSON；含上传素材的版本会导出为包含素材的 JSON 包，在其他服务器导入时需先填写管理员令牌。未经修改的导入文件可用原编号恢复已发布版本。版本绑定当前基础数据，基础数据发生变化后需要先确认兼容性，不能直接当作新版加载。独立 Electron 离线包可选择原版及内置版本；服务器版本管理需要通过游戏服务器访问。

无法读取的单个版本会从列表中跳过，管理页面和游戏版本选择界面会提示数量，其他正常版本仍可使用。服务器日志会记录被跳过的版本编号，管理员可检查版本文件或从备份恢复；服务器不会自动删除或覆盖这些文件。整个版本目录无法访问时，列表仍会报告服务错误。

Compose 将已发布版本及其上传素材保存在 `game_versions` 卷，管理员令牌校验值保存在 `game_admin_token` 卷；`make down` 不会删除它们。删除对应卷会分别删除已发布版本及素材或令牌配置。迁移或备份版本时应保留整个版本目录及其 `assets/` 子目录。直接运行开发服务器时，版本默认保存在 `~/.local/share/threekindoms/versions`，可用 `GAME_VERSION_DIR` 指定其他可写目录；若也需要持久化令牌，设置 `GAME_ADMIN_TOKEN_FILE` 为静态服务目录之外的绝对文件路径。未设置该路径时，直接运行的服务器仅在当前进程内使用令牌。

## 测试

浏览器测试使用项目锁定的 Playwright 驱动本机 Google Chrome 无头模式；先安装 Chrome，并在仓库根目录按锁文件安装开发依赖：

```bash
npm --prefix hd2d-mvp/desktop ci
```

测试使用已安装的 Chrome，不需要另外下载 Playwright 浏览器。也兼容已有的全局 Playwright 安装。

```bash
node --test hd2d-mvp/tests/artcoverage.test.mjs                  # 单个测试文件
node --test --test-concurrency=1 'hd2d-mvp/tests/*.test.mjs'     # 全部测试（较慢，war.test 约 10 分钟）
python3 hd2d-mvp/tests/scenario_server_test.py                  # 游戏版本发布接口与认证
python3 hd2d-mvp/tests/assets_pack_test.py                      # 素材包校验、中断和重试
```

## 打包桌面版

需要 `cwebp`（macOS 上用 `brew install webp` 安装）。

```bash
npm --prefix hd2d-mvp/desktop run dist:mac    # macOS dmg（arm64 与 x64）
npm --prefix hd2d-mvp/desktop run dist:win    # Windows x64 zip
npm --prefix hd2d-mvp/desktop run dist:dir    # 只出 macOS 的 .app 目录，最快
npm --prefix hd2d-mvp/desktop start           # 直接用 Electron 运行游戏（需要先执行一次 build-app）
```

打包命令先运行 `build-app.mjs`，把游戏快照到 `hd2d-mvp/desktop/app/`，产物放在 `hd2d-mvp/desktop/release/`。桌面包将单挑动作转换为无损 WebP，并通过包内素材索引告知游戏使用该格式。

### 正式版本发布

每个正式发布的重大版本都在 [GitHub Releases](https://github.com/jicki/threekindoms/releases) 提供 macOS Apple 芯片与 Intel 的 DMG，以及 Windows x64 ZIP。同步更新桌面版依赖清单和锁文件中的应用版本号，从对应的 `vX.Y.Z` 标签检出并按素材锁构建。

发布前验证安装包完整性，并从打包后的应用进入游戏与单挑。将安装包、SHA-256 校验清单和该版本的独立更新日志一并附到同一个版本标签的 Release。构建素材继续使用独立的 `assets-N` Release。
